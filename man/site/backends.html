The benchmarks call BLAS through its C interface, CBLAS, so the same code runs against any library. The library is chosen when building, with ./configure --with-blas-backend=…; each is built and checked in CI on every change.

Whatever the library, -t sets the thread count through its own interface, and wins over these variables. Each result records the library, and its own version string where it has one (openblas (OpenBLAS 0.3.26 …), aocl (AOCL-BLAS 5.3.2 Build …)).

Where configure looks

For each library, in this order, the last found winning:

  1. where the distribution installs it (Debian and Ubuntu's /usr/include/<triplet>/blis-openmp, Intel's /opt/intel/oneapi/mkl/latest, …);
  2. the variables a module or Spack sets: <NAME>_ROOT, _DIR or _HOME for the prefix, <NAME>_INCDIR and <NAME>_LIBDIR for the directories, with <NAME> the library's (OPENBLAS, BLIS, AOCL, MKL, NVPL, ARMPL, …), and MKLROOT;
  3. --with-blas-incpath=DIR and --with-blas-libpath=DIR, which always win.

OpenBLAS

The default, and what most distributions ship. Its build options (threading, the CPU it was tuned for) are part of its version string, and so of each result.

BLIS

From libblis-openmp-dev on Debian and Ubuntu, which keep its cblas.h in a directory of its own that configure finds. Only its OpenMP or pthreads builds use more than one thread.

AMD AOCL-BLAS

AMD's fork of BLIS, for AMD EPYC. It comes from AMD's installer, a module (AOCL_ROOT) or Spack (^amdblis); no distribution packages it. The benchmarks link its threaded libblis-mt: its libblis is single-threaded, and would ignore -t. AOCL-BLAS may run a small problem on fewer threads than it is given (AOCL Dynamic); only a library built with --disable-aocl-dynamic does not.

Intel MKL

oneAPI MKL, from Intel's repository, a module (MKLROOT) or Spack. It is linked with its GNU OpenMP layer and 32-bit integers (-lmkl_gf_lp64 -lmkl_gnu_thread -lmkl_core). -t sets the thread count of its BLAS domain, which overrides MKL_DOMAIN_NUM_THREADS (a warning says so). MKL may also use fewer threads on a small problem; MKL_DYNAMIC=false makes it use them all.

NVPL and ArmPL

NVIDIA's and Arm's libraries, for aarch64 servers (NVIDIA Grace, Neoverse). Both come from their vendor's apt repository or a module, and take their threads from OpenMP.

Netlib

The reference BLAS: unoptimised, single-threaded, the yardstick the others are measured against. It has no C interface of its own, so the benchmarks bring theirs, over its Fortran routines.

FlexiBLAS

Not a library but a switch: one build, and the library chosen when the benchmark starts, with FLEXIBLAS. Each result names the library FlexiBLAS loaded (flexiblas/openblas-openmp), so the report keeps them apart. Fedora packages it, with OpenBLAS, BLIS and Netlib to load; Debian and Ubuntu do not.

FLEXIBLAS=OPENBLAS-OPENMP bmb_dgemm -m 512:2048 -o openblas.json
FLEXIBLAS=BLIS-OPENMP bmb_dgemm -m 512:2048 -o blis.json

GPU libraries (cuBLAS, rocBLAS, MAGMA, …) are planned for 2.0: see the project.
