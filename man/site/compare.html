The question blas-microbenchmark answers is a comparison: this library against that one, this machine against another, this setting against the default. The benchmarks measure; bmb_report lays the results side by side.

Measure each library

There are two ways to run the same benchmarks against several libraries:

  • A build per library, each in its own directory (see Install). The same commands, run with each build, into separate files: 
    build-openblas/src/c/level3/double/bmb_dgemm -m 128:2048 -t 1:8 -o results/dgemm-openblas.json
build-blis/src/c/level3/double/bmb_dgemm -m 128:2048 -t 1:8 -o results/dgemm-blis.json
  • One build against FlexiBLAS, which loads the library FLEXIBLAS names when the benchmark starts (flexiblas list gives the names): 
    FLEXIBLAS=OPENBLAS-OPENMP bmb_dgemm -m 128:2048 -t 1:8 -o results/dgemm-openblas.json
FLEXIBLAS=BLIS-OPENMP bmb_dgemm -m 128:2048 -t 1:8 -o results/dgemm-blis.json

Every file records the library it ran against, its version, the CPU and the date: the report keeps them apart without you naming them.

Make the report

bmb_report results/*.json > report.html
firefox report.html

The page is a single file, with nothing to fetch: it opens offline, and can be sent as is. For each routine, it shows what the results can support:

  • performance, and bandwidth for levels 1 and 2, against size, with the points where the data leaves the L1, L2 and L3 caches marked;
  • each library against a reference (OpenBLAS, or one you choose on the page), on a log scale where twice as slow and twice as fast sit at the same distance;
  • thread scaling against ideal;
  • a heatmap of every shape, for sweeps over two dimensions (-m and -M);
  • a summary, and every row of every file, sortable.

The Outputs page shows each part.

The whole suite at once

bmb_suite runs every benchmark, or those of some levels, precisions or routines, at the sizes of a profile, into one directory, which bmb_report takes whole. quick measures a few sizes a level, in about a minute; full sweeps from the caches to memory, in several. The options after -- go to every benchmark:

bmb_suite --profile quick -o results -- -t 1,8
bmb_report results > report.html

Its manual, bmb_suite, has the profiles and how to write your own.

Is the difference real?

Two runs of the same command never give quite the same numbers. Run each command several times, each into its own file:

for run in 1 2 3 4; do
    bmb_ddot -v 1024:16777216 -o results/ddot-openblas-$run.json
done

The report then draws a band showing how far the runs spread, and tests each difference between libraries against that spread (a Mann-Whitney U test): a point within the noise is drawn hollow. A comparison from single runs shows the differences, but not which ones to believe.

One library, several versions

Measure three versions or more of the same library on the same machine, and the report adds a history: each routine's performance, version after version, with a version slower than the one before beyond the noise marked slower. The version comes from the library itself, so nothing needs naming.

Two conditions on one machine

To compare a setting rather than a library (turbo, a thread placement, a compiler flag of the library), give each run a label; the report makes a series of each:

bmb_dgemm -m 1024:8192 -l "turbo on" -o results/turbo-on.json
bmb_dgemm -m 1024:8192 -l "turbo off" -o results/turbo-off.json

A fair comparison

  • Same machine, same conditions. A comparison across machines measures the machines.
  • A steady frequency. The performance governor and turbo off, if you can; the benchmark warns when they are not, and the report says under what conditions each series ran.
  • The same threads, pinned. See pinning threads, and Threads.
  • The library's own choices. MKL and AOCL-BLAS may use fewer threads than asked on small problems; see The BLAS libraries.
